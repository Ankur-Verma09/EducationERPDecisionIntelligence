# Phase 3 Canonical Glossary and Representative Schemas

Status: Approved baseline  
Date: 2026-07-29

All examples are generated and fictional. They contain no production or copied ERP
data.

## First-release glossary

| Term | Canonical meaning | Explicit exclusion |
|---|---|---|
| Learner | A tenant-local education participant represented by a generated canonical ID | Not a global person identity; no demographics or contact profile |
| Academic period | A bounded institutional time interval, optionally nested, such as year or term | Not a scheduling calendar |
| Programme | A named course of study owned by a tenant | No eligibility or completion decision |
| Programme version | Effective-dated curriculum identity for a programme | Does not overwrite prior curriculum |
| Course | Stable tenant-local subject/catalog identity | Not a specific delivery |
| Course version | Effective-dated title/credit definition | No grades or outcomes |
| Offering | A delivery of one course version in one academic period and organizational scope | No timetable/room model |
| Enrolment | Effective-dated association of a learner with a programme version or offering | No attendance, marks, fees, health, or discipline |
| Teaching assignment | Association of an existing Phase 2 user with an offering | Does not grant authorization |
| Source system | Registered ERP/logical source within one tenant | No credential storage |
| Source observation | Immutable claim that a source record was observed at a time under a mapping version | No raw payload retention |
| Lineage link | Tenant-consistent association from one source observation to one canonical record | No cross-tenant identity graph |
| Reconciliation issue | A classified mismatch requiring human resolution | No arbitrary free-form source data |

## Identifier rules

- Canonical IDs are UUIDs generated by the platform and never derived from PII.
- Every source record is identified by
  `(tenant_id, source_system_id, entity_type, source_record_key)`.
- `source_record_key` is encrypted/tokenized at rest where configured, is never used
  as a URL identifier, and is exposed only through authorized lineage APIs.
- Institutional learner reference is unique per tenant while active and is masked by
  default.
- Canonical IDs are never reused after retirement.
- There is no platform-global learner identifier.

## Temporal and supersession rules

- Effective intervals are half-open `[effective_from, effective_to)`.
- Null `effective_to` means open-ended.
- Overlapping active versions for the same versioned aggregate are rejected.
- A correction creates a new version/observation and links it to the superseded
  record; prior facts remain queryable to authorized lineage users.
- `observed_at` describes source arrival; effective dates describe business truth.
- Late observations do not silently replace newer effective facts. They create a
  reconciliation issue unless deterministic precedence proves equivalence.

## Conflict precedence

1. Tenant-approved source registration defines authority per entity type.
2. A primary source outranks a secondary source only for its approved entity type.
3. Newer `observed_at` never overrides a higher-authority source by itself.
4. Equivalent normalized values coalesce lineage without changing the canonical
   version.
5. Conflicting equal-authority observations create a reconciliation issue.
6. Human reconciliation requires `reconciliation:manage`, MFA, reason, and audit.
7. Manual corrections change the canonical projection but never alter source
   observations and remain visibly attributed.

## Validation constraints

- codes are trimmed uppercase ASCII plus `-`/`_`, 1–64 characters;
- names are Unicode, normalized, 1–200 characters;
- dates must form valid non-empty intervals;
- credit value is optional, non-negative, and at most 999.99;
- status values come from closed enums;
- unknown fields are rejected;
- source entity type must match a registered authority rule;
- all referenced records must share the same tenant;
- offering campus/department must be consistent with the Phase 2 hierarchy;
- no generated example should resemble real personal information.
